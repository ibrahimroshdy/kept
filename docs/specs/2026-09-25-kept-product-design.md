## 1. What Kept is

A self-hosted, open-source inventory of everything you own and **where it is**: homes,
garages and storage units; the rooms, shelves, boxes and safes inside them; and the things
inside those, from furniture to a single cable.

- **Every thing** carries its paperwork (purchase, invoice, warranties, manual, serial) and its
  life: lent, in repair, sold.
- **Vehicles and machines** carry meter readings, services, fuel and schedules.
- **Locations are shared** with the people who live there, each with a role.

An AI assistant, using whichever provider the owner connects, does two jobs:
- **It fills things in from photos and receipts,** so adding them isn't tedious.
- **It answers and acts:** "where are the spare HDMI cables?", "log 52,340 km on the Corolla".

The same capabilities are exposed over **MCP** to any MCP client, through scoped tokens.

Complexity is chosen per location: **Essentials**, **Household** or **Complete** (D61, D62, D75).

Kept is built as a multi-tenant SaaS from the first line of code. Self-hosting is the same code
running with sign-up closed (D2). A hosted cloud comes later and sells convenience, never
features (D70).

## 2. Why build it

- **Nothing combines these.** Some home-inventory apps have a vehicle category or a single
  mileage field, but none combines readings, services and schedules with an inventory. Vehicle
  apps have no inventory (D129). None of the open-source apps has per-location roles including a viewer, *and* a
  built-in multi-provider assistant, *and* a first-party MCP server with write tools
  ([landscape](../research/2026-09-25-landscape.md)).
- **The existing open-source tools didn't hold up in use.** The maintainer tried and dropped
  Homebox ("UI/feel didn't click"), DumbAssets ("UI too basic") and Shelf.nu (needs the
  Supabase stack). **Polish is the product.**
- **Commercial apps disappear and lock data in.** Encircle's consumer app (Dec 2025) and
  Centriq (Jan 2026) both shut down, and Centriq's export dropped photos and documents.

## 3. Principles

1. **Entering data is the cost that kills these apps.** Every choice is judged by whether it
   makes capture faster. The assistant's first job is capture, not chat.
2. **Evidence is immutable; interpretation is editable.** Receipts, invoices and proof photos
   are kept exactly as uploaded. Fields read from them carry a status each (extracted → confirmed).
3. **The model suggests; code decides.** Dates, intervals, totals and permissions are computed
   in code. Model-proposed writes are confirmed (in-app) or undoable (MCP).
4. **Nothing is invented.** Unknown stays unknown and visible ("needs date", "reading needed",
   "estimated ~14 Nov").
5. **Tenancy is enforced by the database.** Row-level security decides what a request sees.
   "No scope" means refuse.
6. **Your data leaves with you.** Full export at any time, readable without Kept. No limit
   ever blocks viewing, editing or exporting (D72).
7. **Every field has a reader and a writer.** Nothing ships unused.
8. **Features come from explicit decisions,** never from a paragraph of a spec.
9. **Simple by default, deep on demand.** Modules you don't use don't exist for you (D61).
10. **One product.** The self-hosted and cloud editions have the same features (D70).

## 6. Domain model

### 6.1 Tenancy spine

```
User ──1:1── Account ──< Locations it owns (Personal always; others make it a billable owner account)
  │                          ├── Types (tree) · Brands · Vendors · People · Tags · Templates
  │                          └── (cloud) Subscription, only if it owns a non-personal location
  └──< Membership(role, expires_at) >── Location ──> owning Account
Location ── enabled modules / preset, timezone, currency, languages, long-unseen threshold
   ├── Unplaced area (built in)
   └── Places (tree) ──< Things (tree via "inside") ──> Purchase line · Loans · Claims · Warranties · Meters
```

- **Keys:** every owned row carries `location_id` or `owner_account_id`, and every natural
  unique key leads with it (L15).
- **Visibility:** a location's rows are visible when it is one of the current user's
  memberships; one search spans all of them. Account-level rows are visible to members of any
  of that account's locations.
- **Membership:** it can expire (D46); only the owner manages admins (D48).
- **Every user has one account** that owns their Personal location, which is never billed, has no
  other members and no share links. The account becomes a billable owner account only when it owns
  a non-personal location (D114).
- **Managed accounts** (D47) can't own non-personal locations or pay.
- **Moving a thing between owner accounts** copies its type and registry references to the
  destination account.

### 6.2 Places

- **Shape:** a tree under each location. Kinds come from an editable list (floor, room, zone,
  closet, custom) (D33).
- **Location settings:** timezone, default currency, languages (for aliases, D41), optional
  address, enabled modules, "long unseen" threshold (12 months by default, D128).
- **Every location has an *Unplaced* area** for receipts, imports and anything not yet sorted (D118).
- **Places don't move between locations** (D76).
- **Schedules can attach to places** (D39).
- **Terminology:** "area", "room", "spot", "shelf" and "zone" are all **places**. The API and code
  say `place`; the UI says "Add room or spot" for adding structure, which refines the wizard's
  "Rooms" and Add-here's "Area" wording. "Member" means the role; "anyone in the location" includes
  viewers. Prose says "short ID"; the API says `short_code`.

### 6.3 Things

- **Where:** inside exactly one place or one container thing. Loops are refused (D45).
- **Fields:** the built-in fields of D76 plus custom field values, stored as one validated JSON
  document checked against the type.
- **Identity:** a UUIDv7 created on the client (D17, D82), and a **permanent short ID**
  (6 characters, Crockford base32) allocated by the server at sync (D45, D112, D120).
- **Status:** stored lifecycle in use · sold · given away · lost (→ found) · disposed · stolen ·
  destroyed · `returned_to_owner` (D158, D183). *Lent*,
  *borrowed* and *in repair* are derived from open loans and claims (D119).
- **Purchase:** a thing points to a line of a Purchase record, which holds date, vendor, total and
  the receipt (D115).
- **Location display:** the location path shows loans ("with Murdock · due 17 Oct"), repairs
  ("at Samsung Service Centre") and uncertainty.
- **Quantity:** a partial move or loan splits the thing (D10, D57).
- **Containers:** moving one records one event; its contents show "moved with…" and their
  last-seen dates are not updated (D45).

### 6.4 Types

- **Identity:** name, icon, colour, optional parent. Inheritance is a full tree and only adds
  (D12, D92).
- **Capabilities:** *container*, *metered*, *warranty*, *serialized* (quantity forced to 1),
  *consumable*.
- **Field kinds:** text, number with unit, date, select, multi-select, yes/no, URL, money,
  person, vendor, secret, file.
- **Changes preview their impact.** Removed fields are archived. A type in use can't be deleted
  (D92).
- **Built-in types are templates** copied into an account to edit (D92).
- **Default warranty terms** can live on a type or a brand (D55).

### 6.5 Meters, readings, services, fuel, schedules

- **Readings:**
  - One or more meters per thing (km/mi, hours, custom).
  - Readings come from manual entry, READING photos, fuel entries and services, and form one
    series per meter (D52).
  - Readings are ordered by **when they were taken** and checked against their neighbours. A
    reading that doesn't fit goes to the inbox, never a silent rejection; implausible jumps need
    confirmation (D26, D112). A *meter replaced* event records an offset (D52).
  - Meters, readings and service records are core infrastructure, so any metered thing works
    without the Vehicles module (D113).
  - A proof photo is optional (D27).
- **Services:** date, reading, vendor, total, line items, invoice, and which schedules each
  completes (D26).
- **Fuel:** litres or kWh, cost, full or partial fill, station, reading → consumption and cost per
  km (D28).
- **Schedules:**
  - "Every N units and/or M months, whichever first", counted from the last completion. Snooze
    or skip (D29).
  - Distance-based due points are **estimated** from usage and labelled that way (D52).
  - Stale-reading nudges every 30 days by default (D52).
  - Reminders are exactly once per (subject, source, kind, due period), with one delivery per
    user and channel (D111). A reminder source pauses while its module is off (D113).
- **Documents with expiry** (registration, insurance, licence, inspection) remind ahead (D26).

### 6.6 Dates, money, units

- **Dates:** instants are `timestamptz`. Calendar facts are local dates in the location's
  timezone, so "today" means today *there* (L1, D29).
- **Money:** `numeric` plus a currency code. **Supported: USD, CAD, GBP, EUR, EGP** (D136), plus any
  the instance admin enables (D168). Each location has a default currency from the enabled
  currencies; totals show in it, and a view spanning locations groups per currency unless a report
  currency is chosen and rates exist. Conversion uses rates entered on the
  account (or an optional provider). Totals without a rate are never estimated (D76, D136).
- **Units:** set per user; stored values are never converted (D76).

### 6.7 Attachments & evidence

- **Originals:** kept **byte-identical** for RECEIPT, LABEL and READING captures, invoices,
  manuals and warranty documents, and downloadable by members and above only (D117). THING photos
  are shrunk on the phone (D34).
- **Previews:** the phone makes the display JPEG; a HEIC without a preview is stored as "preview
  unavailable" (D36).
- **Processing:** GPS stripping and rotation apply to **derivatives only**; deduplicated by the
  original's content hash per location (D177); PDF thumbnails and extracted text (D77, D117).
- **Limits:** 25 MB per file by default; per-account quota on the cloud (D77).

### 6.8 AI drafts and field status

- **Provenance:** every AI-extracted field carries its status (extracted → confirmed) and links
  to the attachment it came from.
- **What auto-accepts:** name, brand, model, type, colour.
- **What waits for review:** price, dates, serial, readings, and quantity above 1 (D19).
- **Re-running extraction** is explicit, replaces the draft, and every attempt is recorded (D19).

### 6.9 Loans, warranties, claims

- **Loans** point either way (out to a person, in from a person), with due dates and condition
  photos (D56, D57).
- **Warranties** are a list per thing, each with a kind (D53).
- **Claims** track status, reference, costs and documents, and change where the thing reads as
  being (D54).
- Open loans and claims are what make a thing "lent", "borrowed" or "in repair" (D119).

### 6.10 Audit, history, share links

- **Audit:** one central record of every write: actor (user or token), location, entity, action,
  before/after, request ID (D82). Thing timelines, the activity feed and MCP undo (D58) are all
  views of it. **Secret fields appear only as "changed"; money fields are tagged and filtered by
  role in every view; webhooks carry IDs and field names, never values** (D110).
- **Share links** are read-only tokens scoped to one box, place or filtered list, with an
  expiry, limited to inventory pages and a fixed field whitelist: name, photo, type, place path,
  quantity, condition, description (D39, D72, D116).

| Promote, demote or remove admins (D48) | ✓ | – | – | – |
| Location settings and modules | ✓ | ✓ | – | – |
| API/MCP tokens for this location | ✓ | ✓ | own, up to own role | own, read-only |
| Require two-factor for the location; grant support access (D71) | ✓ | – | – | – |
| Transfer or delete the location; billing | ✓ | – | – | – |

Any membership can carry an end date (D46). The Personal location has only its owner (D114).

### 7.2 Sensitive fields (D13, D116)

- **Secrets:**
  - Revealed by admins and above by default; each field's policy can widen that to members or
    named people. Every reveal is explicit and audited.
  - Stored in their own encrypted table, never in the custom-fields JSON, and never indexed for search.
  - **AI tools** (the assistant and MCP together) read a secret only if its field allows it
    (default off).
  - The phone's offline copy **never** holds secrets (D36).
  - Exports exclude them unless chosen, with a passphrase (D68).
  - History records a secret change without its value (D110).
  - Share links never show one.
- **Money:** members and above; hidden from viewers by default, with a per-location toggle.
  Money fields are tagged in the audit and filtered by role everywhere (D110).
- **Share links** show only: name, photo, type, place path, quantity, condition, description (D116).

### 7.3 Tokens and sessions

- **Tokens:**
  - Prefixed (`kpt_`), shown once, stored hashed.
  - Scoped read or read+write, optionally limited to locations; they never exceed the creator's
    role; optional expiry.
  - Rate-limited, and revocable with last-used tracking (D63).
  - Tools are resolved per call against the target location's modules and the token's scope
    (D113, D124).
- **Sessions:** cookie-based with a 30-day sliding expiry and a device list (D49).

## 8. Capture & AI pipeline

1. **Capture (phone, possibly offline):**
   - Choose a mode: THING, RECEIPT, LABEL or READING.
   - The target defaults to the last place or the box just scanned; anything unsorted lands in
     the location's *Unplaced* area (D118).
   - Each capture is queued in IndexedDB with a client UUID and an idempotency key (D17, D34).
2. **Sync:** upload when there's signal. iOS uploads only while the app is open. Replays are
   idempotent. Moves resolve as "latest wins, visibly" (D35). Readings are ordered by when they
   were taken; short IDs are allocated and blank-label claims settled by the server at sync, and
   anything that needs a person's judgement goes to the inbox (D112).
3. **Extract:**
   - One job per attachment on the Postgres queue.
   - The mode picks the prompt. THING may return several objects with bounding boxes → cropped
     drafts (D20; 1.x per D130; provider support is an assumption the evaluation set proves, D129).
   - Aliases are written in the location's languages (D41).
4. **Pace:**
   - Budgets per task and per account; SDK retries off; the first 429 trips a circuit breaker.
   - A length stop counts as failure, and every call is logged in the AI call ledger (D19, L41–L47, §8a).
   - Provider rate limits are paced from the provider's own headers; a budget or cap pauses with a visible "paused until" (§8a).
5. **Review:** the "To review" inbox: accept, edit, bulk actions, merge duplicates (D18, D36).
6. **Other inputs:** email-forwarded receipts (cloud address or self-hosted IMAP, D21),
   barcode (D104), CSV (D73), Homebox (D67), the assistant (D22), MCP (D63).

**AI settings** cascade instance → owner account → user, with a model per task (vision, chat,
embeddings). **Work in a location is paid by the location owner's account**; a personal key
covers only the user's Personal location and threads that don't touch shared data (D121); a turn
spanning locations with different owners is paid by the asking user's own account (D167). Keys are encrypted and never returned to the browser (D19, D15). **With no provider
set, everything still works** (D19). Where keys live, what every call records, cost, caps and pausing: §8a (D206).

## 8a. AI: keys, usage, spend and the call ledger (D206)

Kept tells people **before** they use AI what it will call and roughly what it costs, and
**after** what it called, what that cost and who paid. Owners can cap it. The numbers behind
this section are in the engineering spec §3.5; tables, doors, routes and the pause state
machine are in §7.15.

### Where keys live

AI is configured at three scopes, never per location.

| Scope | Set by | Its key pays for | It never pays for |
|---|---|---|---|
| **Instance** | an instance admin | every location and person with no closer key: the fallback (D19) | nothing is excluded; the instance admin caps it (below) |
| **Owner account** | the account's owner (the person who owns its locations, D114) | **every location the account owns**: each home, garage, storage unit, and its Personal location when the owner has no personal key | another owner's locations |
| **User** (personal) | the person | their **Personal** location, their **private threads** that touch no shared data, and **assistant turns spanning locations of different owners** (D121, D167) | any shared location, including one they administer (D121) |
| **Location** | — | **No key of its own.** A location is paid by its owner's account; a second key per home would make "who pays" ambiguous and scatter one owner's keys | — |

**What each location has instead:**
- **AI on or off:** the AI capture and AI assistant modules (D61), on once a provider resolves (D191).
- **A monthly spend cap** inside the account's cap (below).
- **Its own usage view:** calls, tokens and cost for that location, for its admins and owner.

**Resolution order** (unchanged, D121; step-3 plan Q5), per task:
- **Personal location:** the person's key → their account's key → the instance key.
- **Any other location:** its owner account's key → the instance key.
- **Per task:** the first scope that has a model **for that task** wins. Groq has no embeddings
  model (spike, 2026-09-26), so with a Groq account key, embeddings fall to the instance key if it
  has one, or search stays keyword-only (D200).

AI settings always show the result per task, in words: "Photos and receipts: Groq ·
qwen/qwen3.8-27b · from Alfred's account" · "Search: keyword only (no embeddings model)".

### Who pays, and what it counts against

| Work | Paid by | Counts against |
|---|---|---|
| Reading a photo, receipt, label or meter in a shared location | the location's owner account → the instance | that location's cap, the account's cap, the capturer's person cap, the account's per-task budgets (D19) |
| The same in a Personal location | the person's key → their account → the instance | their personal cap (or the account's caps when the account key pays) |
| An assistant turn about one location, by anyone including a viewer (D123) | that location's owner account → the instance (D167) | as the first row, with the assistant budget |
| An assistant turn spanning locations of different owners | the asker's own key → their account → the instance (D167) | the asker's caps |
| A private thread that touches no shared data | the asker's own key → their account → the instance | the asker's caps |
| Embedding a thing after an edit, and backfills (D200) | the location's owner account → the instance | location and account caps. The person is whoever edited; a backfill is **"Kept (background)"** |
| Embedding a search query (semantic search, D200) | each searched location's payer, once per distinct payer and model | as above |
| "Test connection" | the scope whose key is being tested | that scope's caps |
| Loading a provider's model list (D202) | nobody: not a model call, no tokens | not in the ledger; audited as a settings action |

**Whenever the instance key pays**, the call also counts against the instance's overall cap and
that account's allowance on the instance key, so one household can't spend the instance's key
for everyone.

### The recommended default: Groq with `qwen/qwen3.8-27b`

- **What happens:** pasting a Groq key (recognised by its prefix, D202) pre-selects
  `qwen/qwen3.8-27b` for photos and receipts. The model picker marks it **Recommended**, and the
  AI settings' empty state shows a "Recommended: Groq" card with a link to Groq's key page (the URL
  is taken from Groq's docs at build time).
- **Why, as the settings say it:** "In Kept's test on 2026-09-26 it read receipts, labels and
  nameplates correctly for about USD 0.004 a receipt and 0.003 a nameplate: the cheapest reliable
  result we measured." The measured figures (spike `docs/spikes/2026-09-26-step3-ai-sdk.md`,
  Groq's listed prices that day):

  | Photo | Tokens counted against Groq's limit | Cost |
  |---|---|---|
  | Receipt (English or Arabic) | ~2.2k–2.8k (Groq counts ~2,048 per image) | ≈ USD 0.0039 |
  | Nameplate, LABEL mode | ~2.2k–2.5k | ≈ USD 0.0030 |
  | Odometer, READING mode | ~1.1k reported (~2.2k against the limit) | ≈ USD 0.0012–0.0015 |
  | The 64×64 Test square | ~1.3k | ≈ USD 0.0011 |

- **Said plainly alongside it:**
  - The test was a **synthetic smoke test**; the evaluation set with real photos (V1, V3)
    re-checks the recommendation (V37).
  - It is **Groq's only vision model**, and Groq has **no embeddings model**: semantic search
    needs another scope's embeddings model or stays keyword-only (D200).
  - The key tier measured allowed **8,000 tokens a minute, about 2–3 photos a minute**. Kept paces
    to the provider's limit, so a 30-photo session is named over roughly 10–15 minutes while
    capture carries on.
  - Reading confidence isn't calibrated (one odometer image gave two different values, both at
    0.98), which is why readings always wait for review (D19).
- **The others stay first-class** (D202): OpenAI, Anthropic, Google, OpenRouter and custom
  OpenAI-compatible endpoints (Ollama, LM Studio). The recommendation is dated in
  `DEFAULT_MODELS` (`asOf`) and revisited whenever the evaluation runs.

### The AI call ledger

**Every call is one row**, including failures and calls Kept held back. A retry is a new row with
the same request id and the next attempt number (L47).

| Recorded | Detail |
|---|---|
| When and which | time; request id (the HTTP request or job that caused it); attempt number |
| Provider and model | provider kind, the provider config used, the model id, the reasoning level, the prompt version |
| What for | the task: thing, receipt, label or reading extraction · assistant turn · assistant tool follow-up · thing embedding · query embedding · connection test |
| Where and who | location (none for private threads and cross-owner turns); the person ("Kept (background)" for backfills) |
| Who paid | the paying scope (instance · account · user), the paying account or person, and whether it **fell back** past a closer scope |
| Tokens | input, output, reasoning and cached-input tokens; Kept's estimate before the call |
| Images | how many; the per-image token estimate; the total bytes sent. Never the image; the attachment ids only (D163) |
| How it went | latency, the provider's finish reason, the outcome (below), a short error code, whether it was sent at all |
| Cost | amount, currency, **source** (provider-reported · price table · unknown), and the price-table version used |
| What it served | the extraction, the assistant thread, the thing (for extraction and embeddings) |

**Outcomes:**

| Outcome | Meaning |
|---|---|
| `ok` | a usable answer |
| `refused` | the provider declined: a content filter or a safety refusal |
| `rate_limited` | the provider said 429 or quota, or Kept's pacer or breaker held the call back |
| `over_budget` | Kept didn't send it: a cap or a budget was reached |
| `provider_error` | the key was rejected, a 5xx, a network failure, or an error inside a 200 (spike finding 7) |
| `timeout` | no answer within the call's timeout |
| `schema_invalid` | an answer that isn't the JSON asked for |
| `truncated` | stopped at the output limit; a failure, never auto-retried (L42) |

Rows for calls Kept never sent (`over_budget`, and `rate_limited` held by Kept) carry no tokens
and no cost, so the ledger shows what was attempted as well as what was spent. **A short wait for
the provider's per-minute window is not a row;** only a hold that pauses work is.

**Never recorded:** the prompt, the image, the reply text, the key, secret values, or the
provider's error message (its text can echo the request; the spike saw OpenRouter echo an account
id). What an extraction produced lives in the extraction itself (§6.8); what the assistant said
lives in the private thread (D23).

### Cost

1. **The provider's own figure wins.** OpenRouter reports each call's cost in its usage; that
   amount and currency are recorded with source "provider".
2. **Otherwise, the price table.** An instance admin keeps a table per provider and model: input,
   output, reasoning (defaults to output) and cached-input rates per million tokens, an optional
   per-image rate, a currency, and the date it takes effect. **Editing a price adds a new version;
   it never rewrites the past**, so each call keeps the price it was costed with. A price can be
   **prefilled from the provider's model listing** where it carries prices (Groq and OpenRouter
   do, per token in USD), shown with the listing's date for the admin to confirm; OpenRouter's
   `-1` router prices are skipped.
3. **No price, no guess.** A call without a provider figure or a price row has **cost unknown**.
   Usage shows "N calls with unknown cost" beside every total, and a money cap says it can't see
   them (below).
4. **Totals are per currency**, never converted without a rate (D76). A money cap compares costs
   in its own currency, plus costs in another currency only where the account has an exchange
   rate for that pair (converted at that rate, and labelled so).
5. **Displayed with "≈"** and to 4 decimal places below 0.01, so a USD 0.0039 call never reads as
   "0.00".

### Limits and pausing

**Caps are monthly, in money and/or tokens.** No cap is set by default; setup suggests one (§3.5).

| Cap | Set by | Counts |
|---|---|---|
| Instance, overall | an instance admin | every call the instance key pays |
| Instance, per account | an instance admin (a default for all accounts, overridable per account) | calls the instance key pays for one account's locations and people |
| Account | the account's owner | every call the account's key pays |
| Location | the location's owner | every call for work in that location, whichever key pays; **at most the account's cap** |
| Person within an account | the account's owner | one person's calls in the account's locations |
| Personal key | the person | every call their own key pays |
| Per-task budgets (D19) | whoever sets that scope | tokens per minute, day and month per task, at the instance and account |

- **The tightest applicable cap wins**, and the pause names it.
- Location caps are ceilings, not shares: several locations' caps may add up to more than the
  account's.
- Costs are final only after a call returns, so **a cap can be overshot by the calls already in
  flight** (at most the concurrent calls allowed per payer, §3.5). Kept reserves each call's
  estimated cost before sending to keep that small.
- A money cap can't count calls of **unknown cost**. When they exist, the cap shows "N calls this
  month have no price and aren't counted. Add prices, or set a token cap too."

**Warnings and the pause:**

| At | Who hears | How |
|---|---|---|
| **80%** of a cap, once per month | whoever set the cap; for a location cap, its owner and admins; for a person cap, that person and the owner | in-app (the AI status line, the usage page, and the notification centre from step 4), email, and for the instance caps an **admin alert** (D166) |
| **100%** | the same | the same, and the scope **pauses** |

**What people see, and what happens to work:**

| State | Shown | Work | Ends |
|---|---|---|---|
| Active | nothing extra | normal | — |
| Nearing (80% or more) | "80% of Home's AI cap used so far this month" on AI settings and usage | normal | the month rolls over, or the cap is raised |
| **Paused: cap** | **"AI paused until 1 Oct · Home's monthly cap reached"** on Capture, the inbox and drafts, a thing's extraction status, the assistant (disabled with the reason, screens §3), Search ("semantic search paused, keyword results only"), AI settings, and Home's attention panel for owners | **captures still save**; extraction is queued as paused and runs when the pause ends; the assistant can't be asked | 00:00 UTC on the 1st (D188), or **Resume now** |
| **Paused: by hand** | "AI paused by Alfred" | the same | Resume |
| **Waiting for the provider** | "Waiting for Groq · about 20 s", on progress lines only, never a banner | calls are held by the pacer, never failed | the provider's reset time |
| **Provider unavailable** | "Groq isn't answering · retrying at 14:05" | work waits | the breaker's retry (L45) |
| **Key rejected** | managers: "Groq rejected the key · Replace key"; others: "AI isn't working here · ask Alfred" | work waits | the key is replaced |

**Resume now** is for whoever set the cap (the owner; an instance admin for instance caps). It
opens a sheet: "Home has used USD 5.00 of USD 5.00 this month · Raise to [6.25] · Remove the
cap · Keep paused". Raising or removing it resumes paused work at once, oldest first and paced.
Others see "Ask Alfred to resume".

**Provider rate limits are not budget pauses.** The pacer reads the provider's rate-limit headers
(on Groq: remaining tokens and the reset time) and holds the next call before the provider
refuses it. Groq keys make **one call at a time**. The first 429 trips the breaker (L45).

### Retention and privacy

- **Kept 13 months** (a full year plus the month to compare), in monthly partitions dropped
  whole. Before a partition is dropped its **monthly totals** (per payer, location, person, task,
  model and currency) are kept for 5 years, so a year-on-year chart still works. An instance
  admin can change the 13 months (§3.5).
- **Who sees which rows:**

  | Role | Sees |
  |---|---|
  | Anyone (members, viewers) | their own calls, everywhere |
  | Admin of a location | every call in that location |
  | Owner | every call in their locations, and every call their account's key paid |
  | Instance admin | **totals per account**; the **detail of calls the instance key paid** (time, account, person, task, model, tokens, images, cost, outcome), with **no location name, thing or thread**; never another tenant's per-location detail (D33, D71) |

- **Money** in the ledger follows the location's money gate: viewers see tokens, and cost only
  where the location shows money to viewers (D13, D110).
- **An assistant thread's link** shows only to its owner (D23). Admins see "assistant question"
  with the tokens and cost.
- **Exports:** a location's export includes its ledger as `ai-calls.csv` (money per the gate, no
  thread ids). **Deleting a person** keeps their rows for the payer, shown as "a deleted person".
- **Data use per provider (D83, L63).** Beside each provider choice: what Kept sends it
  (**only an EXIF-stripped image, never the original** (D163, D202); for extraction, the fixed
  prompt and the location's languages; for the assistant, the question and the tool results it
  asked for within the asker's role; for embeddings, the fields D200 lists; **never secret
  values**), and a dated summary of the provider's own retention and training terms with a link
  to its policy, checked against its current terms before each release (screens §8).

## 9. Search

- **Engine:** Postgres full-text plus `pg_trgm` fuzzy matching, with Arabic normalisation at
  index and query time (D42).
- **Searchable:** names, aliases, brand, model, serial, notes, custom fields, tags, place paths,
  vendor and person names, extracted receipt text.
- **Semantic search** with pgvector merges with keyword results by reciprocal rank fusion, from
  build step 6; keyword-only while nothing is embedded (D42, D200).
- **Scope:** every query runs under RLS across the user's memberships. Secret values are never
  indexed (D116); money is hidden for viewers.
- **Result rows** always show the full path, including loan, repair and uncertainty states.

## 12. Architecture

- **Monorepo** (pnpm): `apps/server` (Fastify), `apps/web` (React + Vite PWA), `packages/shared`
  (zod schemas and types), `packages/mcp` (D81). Home Assistant is a separate Python repo (D59).
- **One image**, with `web` and `worker` roles and a single-process mode. It is stateless, so the
  cloud runs several replicas (D81).
- **PostgreSQL 18** (18.6 current; 19 adopted once GA and supported by pgvector, D128) with
  pgvector, pg_trgm and unaccent (D82).
  - **Roles:** an owner role runs migrations; a non-superuser app role serves requests, and the
    app refuses to start without it.
  - **Isolation:** RLS on every owned table, `security_invoker` views, a leak test in CI.
  - **Everything else in Postgres:** the job queue, full-text search and vectors (D82, D92).
- **Storage:** one interface over local disk or S3; signed URLs on S3 (D77).
- **AI:** the Vercel AI SDK behind Kept's own pacing, budgets, circuit breaker and call log
  (D3, D19).
- **MCP:** stateless Streamable HTTP. Thin tools call Kept's own routes with the caller's
  token, so validation, permissions and audit are shared (D15, D63).
- **API:** `/api/v1`, OpenAPI generated from route schemas; the web app is a client of the same
  API. Signed, retried webhooks (D60, D63).
- **Offline:** a Serwist service worker for the shell; a Dexie (IndexedDB) capture queue and a
  read-only snapshot, synced on open and focus (D17, D36, D101).
- **Libraries (verified):**
  - Better Auth, including OAuth 2.1 for MCP (D93).
  - pg-boss (D94).
  - React Aria Components through shadcn (D95).
  - Lingui (D96).
  - Lucide + Tabler icons (D98).
  - The official MCP TypeScript SDK **v2** (required by the 2026-07-28 spec and Better Auth's MCP plugin).
  - Drizzle RLS through a per-request wrapper (D100).

## 13. Security & threat model

| Threat | Mitigation |
|---|---|
| One tenant reads another's data | RLS with a non-owner role; "no scope = refuse"; `security_invoker` views; schema-wide leak test; natural keys lead with the tenant (D82, L25–L28) |
| Stolen token | Scoped, location-limited, expiring, revocable; can't exceed its creator's role; no destructive MCP tools; 7-day undo; rate limits (D58, D63) |
| Prompt injection via receipts, manuals, labels | Documents are data, never instructions; in-app writes need a confirmation card bound to its arguments; MCP writes are audited and undoable; tools are limited by role (D22, D58, L55, L56) |
| SSRF through any user-supplied outbound target (AI base URLs, webhooks, ntfy, Apprise, IMAP hosts, OIDC issuers, Homebox URL, barcode endpoints) | Private ranges blocked on the cloud; an admin opt-in on self-hosts; manual links are never fetched by the server (D83, D128) |
| Malicious uploads | Magic-byte checks, SVG rasterised, non-images served as attachments with nosniff and a sandbox CSP from a cookie-less path; images re-encoded with a pixel limit; PDFs parsed in a limited child process; scanning in the cloud phase (D77, D157) |
| Hostile imports | IDs, never archive paths, become storage keys; symlinks rejected; size, ratio and entry caps (D157) |
| Formula injection in exported CSVs | Cells beginning with `= + - @`, tab or CR are neutralised (D169) |
| Lost updates between people | Row versions and conflict handling (D156) |
| Account takeover | Passkeys and TOTP, owner-enforceable two-factor, rate-limited credential routes, device list (D49, D50, L34) |
| First-run hijack | One-time setup code from the logs (D32) |
| Lost secret key = unreadable secrets | Recovery kit, setup acknowledgement, status-page nag (D66) |
| Leaky exports and lost phones | Secrets excluded unless chosen and passphrase-encrypted; the offline copy never holds secrets and is wiped on logout (D36, D68) |
| The operator snooping | **An application-level policy:** the instance admin has no in-app data access, and support access is only when granted, time-boxed and audited. An operator with database access can bypass this, so the cloud needs operational controls and audit (D33, D71, D129) |
| Secrets or prices leaking through history, feeds, undo or webhooks | Secret changes recorded without values; money tagged and filtered by role in every view; webhooks carry IDs and field names only; covered by the leak test (D110) |
| Share links exposing too much | A fixed field whitelist: never money, secrets, serials, people, loans or documents (D116) |
| Auto-approving MCP clients | Safety doesn't rely on client prompts: scope, audit, 7-day undo that refuses if the field changed since, no destructive tools (D124) |

## 14. Operations

- **Backups:** a nightly consistent snapshot through the bundled restic to S3/B2/R2, SFTP, a NAS
  or local disk: DB + files when stored locally, or DB + manifest with S3 versioning (D144), plus
  the readable export (D159). Encrypted, deduplicated, retention 7/4/6. A size
  check and a stale alert (D64, D66).
- **Upgrades:** an automatic snapshot first; migrations run once under a lock; one-version rollback
  (D66). The update check is opt-in (D65).
- **Health:** `/healthz`, `/readyz`, `/metrics`, and an admin status page. The key alarm is
  "reminders not scanned" (D66).
- **Restore:** into a new database, verify, then swap; a monthly nudge to test it (D66).
- **Packaging:** multi-arch images, Docker Compose (optional Ollama profile) and a Helm chart
  (D16, D85), plus an optional `pdf` sidecar (D97). Store listings after 1.0 (D107). HTTPS is
  guided, not required (D31).
- **No telemetry** (D84).
