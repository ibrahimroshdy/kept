# The RLS benchmark at 10,000 things

Step 2, task 24. It answers risk #3 in the master plan, "RLS cost on a Pi". *(Since D209, 2026-09-27, the floor is any 2 GB, 2-core machine rather than a Pi; read "Pi" below as that floor. The V5 run happens on a 2 GB, 2-vCPU VM.)* Run on 2026-09-26/27.

**Verdict.** On the gate pass (`bench:pi`: Postgres limited to 1 CPU and 1 GB, node to a 512 MB
heap), every read and search path is inside its budget for all three
actors, the move of 200 things is well inside 1 s, and every RLS helper function runs once per
statement. Before the fixes, text search spent ~170 ms a request reading every visible thing, and
typo search missed its budget. The cause was RLS itself: PostgreSQL may not use a
non-leakproof operator (`@@`, pg_trgm's `%`) as an index condition ahead of a policy. Migration
0030 moves the text match behind two definer doors, which cut search to 20–40 ms. Three more
fixes landed alongside it: the trash list's batch count, the place-contents breadcrumb, and a
serial index.

On the final gate pass nothing misses: 76 path × actor measurements, no budget miss, no helper
run per row. The slower-core proxy (below) says the Pi run before 1.0 still matters, mostly for
writes (a 200-thing move at ~0.7–1 s p50) and for p95 tails. Search is ~2× under budget at p50 there.

**What the tool does:**
- It creates its own scratch database (`kept_bench_<id>`), migrates it and seeds it. It never
  touches the dev `kept` database, and it drops the scratch database at the end.
- It starts the real server (`startKept`) on a loopback port with `KEPT_ROLE=web`. That gives
  pg-boss for enqueues, local file storage and Better Auth, and no job worker competing.
- It signs in the three actors and times each path over HTTP with `fetch`, one request at a
  time: 20 warm-ups, then 200 timed runs. Moves use 2 warm-ups and 60 runs, there and back.
  The bulk tag uses 30 runs. Previews use 50 runs, to stay under the route's 60-a-minute limit.
- Latency is client-side, from request to the last byte of the body. It includes zod, the
  session lookup and serialisation.

**The passes:**

| Pass | Postgres | Node | What it stands for |
|---|---|---|---|
| unconstrained | the shared dev container on 5452 (other agents' test runs were using it at the same time: noisy) | default heap | the laptop |
| **gate** (`bench:pi`) | its own container on 5462: `--cpus 1 --memory 1g --memory-swap 1g` | `--max-old-space-size=512` | the task's Pi-class constraints: one core's worth of CPU and a Pi-sized memory |
| slower-core proxy (`bench:pi-speed`) | the same container at `--cpus 0.3` | 512 MB heap, pinned to the efficiency cores (`taskpolicy -b`) | a CPU several times slower per query, as a Pi 4's Cortex-A72 is next to an M1 Pro core |

The gate pass limits parallelism and memory. It does not make any one query slower: a single
query never used more than one core anyway. So a gate-pass figure is a laptop-speed figure
under Pi memory.

The slower-core proxy stands in for per-query CPU cost, and it overstates the tails:
- `--cpus 0.3` is a CFS quota of 30 ms per 100 ms period. A request that needs more than 30 ms
  of Postgres CPU in one period waits out the rest of it, so its p95 and p99 carry
  throttling stalls a real core would not have.
- A Pi 4 has four cores, and here Postgres's background work (autovacuum, the WAL writer, the
  checkpointer) shares one throttled third of one.

How close the proxy's per-query speed is to a Pi 4's is **inferred, not measured**. The rough
ratio of a Cortex-A72 to an M1 Pro performance core puts a Pi between the gate pass and this
proxy for p50. Only a run on a Pi settles it: V5, before 1.0.

**Budgets:**
- From engineering spec §3.1 and plan T24: p95 < 300 ms for page loads and search, < 200 ms for
  the thing page, and < 1 s for moving 200 things.
- The bulk tag is held to the move's 1 s. The plan gives it no budget.
- The laptop gates of plan T24 (search < 100, thing page < 60, contents and lists < 80) are
  printed beside the unconstrained pass.
- Every table cell below is `p50 / p95` in milliseconds for the **worst of the three actors**.
  ✗ marks a miss.

## Plans

The tool traces the SQL of one run of every read path. It then EXPLAINs (ANALYZE, BUFFERS,
VERBOSE) the three slowest statements of each, as `kept_app`, in the owner's scope and in the
viewer's.

**RLS helpers run once per statement.** Across 120 plans, the tool found
`visible_location_ids()` (and `visible_account_ids()` or `admin_*_ids()` where a policy uses
them) at 162 plan nodes:
- Every one ran `loops=1` or was never executed.
- No scope column was compared to a SubPlan that wasn't hashed.
- Each call is a `ProjectSet` under a **hashed SubPlan**. The policy's `location_id IN (SELECT
  kept.visible_location_ids())` is evaluated once into a hash table, and each row probes it.
- This holds inside per-row SubPlans too: a thumbnail's `attachments` lookup at `loops=21` still
  shows its hashed helper at `loops=1`.

The RLS form in 0006/0016 therefore needs no change. The planner treats `IN (SELECT srf())` the
way the plan wanted `(SELECT …)` to be treated.

**Index use on `location_id`:**
- With an explicit location (location page, location things list, trash, activity by
  location), the plans use the composite indexes that lead with `location_id`: things_name_sort,
  things_trash, audit `location_id, at`.
- Place contents use `things_place_idx`, and the thing page uses primary keys.
- The global lists (things across 3 locations, Home's counts) Seq Scan `things`. With no location
  in the query, the policy's hashed probe is the only filter. At 12,750 rows that is 5–10 ms on
  the laptop, and it grows linearly with the instance (see Follow-ups).

**What the fixes changed in the plans:**

1. **Text search** (`search: hdmi`, before):
   ```
   Seq Scan on things t_1  (actual time=0.295..207.668 rows=209 loops=1)
     Filter: ((deleted_at IS NULL) AND (ANY (location_id = (hashed SubPlan 44).col1))
              AND ((search_tsv @@ '''hdmi'':*'::tsquery) OR … OR (kept."normalize"(name) % 'hdmi')
              OR (kept."normalize"(serial) = 'hdmi')))
     Rows Removed by Filter: 12601
   Execution Time: 214.203 ms
   ```
   Why it was a Seq Scan:
   - `@@` (ts_match_vq) and `%` (similarity_op) have `proleakproof = false`.
   - A policy's qual comes first. A user qual can be an index condition ahead of it only if it
     is leakproof.
   - So under RLS, no search could use `things_search_idx` or `things_name_trgm`. Each search
     read every visible thing and ran `kept.normalize()` on every name and serial.
   - With `SET enable_seqscan = off` the planner found no bitmap path at all. That confirms the
     cause is the barrier, not costing.

   After: `t.id IN (SELECT kept.search_thing_ids(…) UNION ALL <short-code ids>)`. The door
   runs a BitmapOr over the GIN, trigram and new serial indexes as kept_owner. Then:
   ```
   Nested Loop  (actual time=0.991..3.153 rows=209 loops=1)
     ->  … search_thing_ids …  rows=209
     ->  Index Scan using things_pkey on things t_1  (loops=209)
   Execution Time: 5.689 ms
   ```
2. **Did-you-mean** (`search: typo`):
   - Before, it normalised and re-parsed every visible name per row: 266 ms.
   - `kept.near_thing_names()` reads the visible names' and aliases' lexemes once through
     `ts_stat`. It finds the things holding a near word through the GIN index, and trigram
     neighbours through `things_name_trgm`: 14 ms.
3. **Trash list:**
   - The batch-size subquery (`location_id = … AND trash_batch_id = …`) had only the
     `location_id`-leading `things_barcode_idx`. Each row of the page bitmap-scanned the
     location's whole heap: 10,209 rows removed per row, 51,459 heap blocks for a 50-row page,
     285 ms.
   - Partial indexes on `(location_id, trash_batch_id) WHERE trash_batch_id IS NOT NULL` make it
     an Index Only Scan: 7 ms.
4. **Place contents:**
   - Every row ran `kept.path_of()` and the Unplaced lookups for its breadcrumb. Each is a
     plpgsql function whose own statements go through the policies again, for up to 200 rows.
   - The rows are all directly in the place, so they share its breadcrumb. The route now reads
     it once.

**Remaining full scans worth knowing** (fine at 10,000 things, and linear in the instance):
- Home's two aggregates (thing counts per location, and the attention counts) each Seq Scan
  every visible thing: ~7 + 29 ms on the laptop, 110–175 ms p50 (p95 ~400 ms) on the proxy: Home is the one page that misses on the proxy in every version.
- The contents query's `is_container` EXISTS is planned as one hashed SubPlan over all visible
  things: ~5 ms.

**Why doors and not `ALTER FUNCTION … LEAKPROOF`:**
- Marking `ts_match_vq` and `similarity_op` leakproof needs a superuser, and managed Postgres
  won't grant it.
- It would hold for every table, including ones whose policies were written assuming those
  operators run after them.
- The doors return only ids, or names, of things the caller can already select. They apply the
  caller's visibility themselves, from `app.user_id`. The rows themselves are still read through
  the policies.

## Conclusions

1. **Risk #3 is answered for step 2 on the laptop proxy.** RLS costs one hashed probe per row
   scanned. The helper functions run once per statement. With the fixes, every read and search
   path is well inside its budget on the gate pass.
2. **The real RLS cost was not the helpers.** It was the index conditions the security barrier
   forbids. Any future query that filters on a non-leakproof operator (full text, trigram,
   `ILIKE`, JSON containment) over a large table will seq-scan under RLS. Such queries need a
   door like 0030's, or a leakproof formulation. **Check with EXPLAIN as kept_app, not as the
   owner.** This belongs in the engineering spec's RLS notes.
3. **Writes are where a Pi will hurt, and the tails come from contention.** On the final gate
   pass a 200-thing move is 149 ms p50 / 189 ms p95 within a location and 205 / 446 ms across
   locations; the bulk tag (20 PATCHes) is 495 / 780 ms. The same write paths spiked on other
   passes (bulk tag p95 1.3 s on the "after" gate pass, 1.26 s on the final unconstrained pass),
   with p50 unchanged: the spikes track what else was running on the machine (other agents'
   test suites share the laptop and, on the unconstrained pass, the database), not the code,
   which did not change between those passes. On the slower-core proxy a 200-thing move takes
   0.7–1 s at p50 and several seconds at p95 (CFS throttling inflates those tails, see Method).
   Whether a Pi core lands inside 1 s is **inferred, not measured**: it depends on the Pi being
   faster per query than a third of an M1 Pro core, which the rough core ratio suggests but does
   not settle.
4. **A Pi run is still due before 1.0 (V5).** The tool runs as is on an arm64 box with Docker:
   `pnpm --filter @kept/server bench:pi` without the CPU limit.

## Follow-ups (not done here)

- **Write path cost on a slow core.** A 200-thing move writes 200 `thing.move` audit rows,
  their subjects, tombstones and a reindex enqueue in one transaction. Profile it on the Pi
  before optimising.
- **A bulk-tag route.** Today a bulk tag is 20 separate PATCHes, each a transaction with its
  own audit row and If-Match. One route (like the move's) would make it one transaction. That
  is a step-3 API decision, not a fix.
- **Home and the global lists at 50,000 things** (the §3.1 instance maximum). The counts are
  full aggregates over the visible things. If the Pi run shows them growing past budget, keep
  per-location counts, since `things` already has triggers.
