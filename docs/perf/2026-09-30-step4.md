# Step 4 performance: Home's agenda, the reminder scan and the notification count

This covers the "Perf" item of step 4, task 30. The figures were measured on 2026-09-30 between
12:09 and 12:15 (Cairo, EEST): three full runs of `apps/server/test/perf/step4.perf.test.ts`,
plus one diagnostic run that breaks Home's read down by query.

**Verdict** (the first three runs; §1 "After the first fix" has the later ones: 144 ms p95 at
load 8–9, passing narrowly).
- **Home's agenda counts miss the provisional target.** The target is a p95 under 150 ms at
  10,000 things. The measured p95 was 232–295 ms, and the p50 about 220 ms, in every run. The
  cause is the query itself, not machine noise: each read of `public.agenda_items` costs about
  95 ms, and Home reads the view twice (see §1). The test keeps the 150 ms limit, so
  `ci-local.sh perf` fails on this case until it is fixed.
- **A full reminder scan pass meets its target.** At this size it takes 2.3–2.8 s against the
  plan's 20 s, well inside the job's `expireInSeconds: 60` (`jobs/policies.ts`). The pass
  writes 600 new occurrences, 1,200 notifications and 1,200 deliveries. A steady pass, with
  nothing new, takes about 0.1 s. The test's limit is tightened to 10 s.
- **The notification count meets its target.** The p95 is 5.4–6.2 ms against 20 ms. That
  limit is kept.

## The fixture

One household location (Home, Africa/Cairo), owned by Ibrahim, with Bruce (admin), Louis
(member) and Talia (viewer). It has 20 places and 10,000 things, and the things carry:

- 2,000 warranties: ends spread from 120 days ago to 609 days ahead, with a 30-day lead. Every
  tenth one is unregistered and has a registration deadline.
- 500 schedules, every 3, 6 or 12 months, with anchors spread over the last 400 days.
- 300 open loans to or from Murdock: a fifth are borrowed in, and due dates run from 30 days ago
  to 59 days ahead.
- 200 expiring documents: 150 on things and 50 on a place.

On the day of the runs this gives Home 429 overdue, 71 due and 103 expiring rows. The
location, the people and the memberships go through the API. The source rows are bulk-inserted
with SQL as kept_owner, with every trigger firing, and then ANALYZEd. Building them through the
API would take longer than the checks themselves. Seeding takes 3.7–3.9 s. The requests go
through the app in-process (fastify inject), so the figures are server time.

## 1. Home's agenda counts (`GET /api/v1/home`)

The owner's `GET /api/v1/home` is `home/service.ts` `homeOf`: the agenda counts
(`agendaCounts`), the per-source split (`agendaCountsBySource`), the open loans, the location
cards and the checklist facts. There are 5 warm-ups, then 50 timed reads.
`GET /api/v1/agenda`'s first page is timed the same way and recorded; the plan sets no target
for it.

| Run | Load avg | Home p50 / p95 / max (ms) | 150 ms p95 target | Agenda first page p50 / p95 / max (ms) |
|---|---|---|---|---|
| 12:09 | 2.8–5.5 | 217.6 / **294.6** / 359.2 | **MISS** | 226.4 / 317.8 / 352.5 |
| 12:10 (rerun) | 4.1–5.4 | 222.8 / **231.7** / 232.9 | **MISS** | 200.7 / 211.5 / 239.0 |
| 12:15 (final) | 8.1–11.7 | 223.4 / **249.2** / 250.8 | **MISS** | 198.9 / 209.1 / 211.0 |

**Where the time goes.** The diagnostic run (12:13, load 11.3) timed each query on its own, as
the owner on kept_app, over 20 reads:

| Query | p50 (ms) | p95 (ms) |
|---|---|---|
| `agendaCounts(client, {})` | 94.2 | 151.4 |
| `agendaCountsBySource(client)` | 99.4 | 121.8 |
| `SELECT count(*) FROM public.agenda_items` | 96.5 | 103.6 |
| the whole `homeOf` | 215.0 | 218.2 |

- **Most of Home's time is the view, read twice.** The rest of `homeOf` takes about 20 ms. The
  per-source counts already contain the totals, so one read could serve both.
- **Each view read is about 95 ms,** and `EXPLAIN ANALYZE` shows why: `kept.module_on()` is
  called as a function for every source row, in each branch's filter. Among 2,000 warranties
  that call accounts for 43 ms of the 97 ms. `module_on` is a SQL function with
  `SET search_path`, and Postgres never inlines a function that has a SET clause. The plan
  shows it evaluated per row rather than once per location.
- **Row-level security's own cost is small.** `kept.visible_location_ids()` takes 0.5 ms, and
  in the plan each branch's hashed visibility filter finishes in well under 0.1 ms.

Two fixes would likely bring Home well under 150 ms, though neither has been measured:

- compute `agendaCounts` from `agendaCountsBySource`'s rows, so the view is read once;
- decide each location's module state once, in the view's `loc` CTE, instead of per row, or
  make `module_on` inlinable.

The first is local to `home/service.ts`, and T30 made it (below). The second changes migration
0053's view, which the reminder scan, the agenda and the Schedules screen share, so it is carried
over rather than made in a finishing task.

## 2. A full reminder scan pass (`reminders/scan.ts` `runScan`)

This is the function the `reminder-scan` job calls (`reminders/jobs.ts`). A full pass writes
every occurrence as new: each one gets its own transaction, a notification and an email
delivery for the owner and the admin, and a `reminder-deliver` job for each overdue one. The
member and the viewer receive nothing by default (Q8). The test runs 1 warm-up pass and then 3
timed passes, deleting the location's occurrences before each; the notifications and deliveries
go with them by cascade. It then runs 3 steady passes, with nothing new, as every later
15-minute pass is.

The senders and the job queue are recorders. The real `send` inserts a pg-boss job for each
overdue delivery in the same transaction (700 jobs per pass here), so the real pass costs a
little more than these figures.

| Run | Load avg | Full pass p50 / max (ms) | Occurrences / notifications / deliveries | Steady pass p50 / max (ms) | 20 s target |
|---|---|---|---|---|---|
| 12:09 | 2.8–5.5 | 2497.9 / 2710.5 | 600 / 1,200 / 1,200 | 102.2 / 103.9 | ok |
| 12:10 | 4.1–5.4 | 2262.9 / 2370.6 | 600 / 1,200 / 1,200 | 102.0 / 103.2 | ok |
| 12:15 | 8.1–11.7 | 2526.0 / 2823.7 | 600 / 1,200 / 1,200 | 107.0 / 112.8 | ok |

That is about 4 ms per new occurrence, with its fan-out. The pass is bound by its one
transaction per occurrence, which is by design (scan.ts: each occurrence is written whole or
not at all). **Limit set:** the worst pass must be under **10 s**, about 3.5 times the worst
measured, and tighter than the plan's 20 s.

## Targets missed

- **Home's agenda counts:** p95 232–295 ms against the provisional 150 ms, in all three runs.
  After 4913da8: 144 ms at load 8–9 (passes, narrowly), 161–217 ms under load 13–37 (misses).
  The cause is in §1. Until it is fixed, `step4.perf.test.ts`'s first case fails, and so does
  `bash scripts/ci-local.sh`'s `perf` step. The limit was not raised to hide the miss.

Results are written to `.tmp/perf/step4.json` (git-ignored). The `perf` step in
`scripts/ci-local.sh` already runs everything under `test/perf` through
`vitest.perf.config.ts`, so this file needs no CI change.
