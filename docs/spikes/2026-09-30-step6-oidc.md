# Spike S6.7: generic OIDC with Better Auth's `genericOAuth`

Date: 2026-09-30. Step-6 plan, Task 0 (it feeds T7, T16 and T22). Result: **pass, with named
Kept-side fixes.** All six checks hold on a local mock provider, 48 of 48 cases.
- **Stock `genericOAuth` does not meet them.** With Better Auth's defaults it auto-links on a
  verified email, signs up anyone, accepts `.invalid` addresses, and fetches discovery with the
  global `fetch`, outside the SSRF guard. Each gap was reproduced in this run ("Stock, for
  comparison" below).
- **Every gap has a Kept-side fix, and each fix ran green:**
  - Better Auth options: `account.accountLinking.disableImplicitLinking` and
    `user.validateUserInfo`;
  - a small `kept-oidc` plugin (two before-hooks);
  - explicit endpoints, with `getToken`/`getUserInfo` going through `guardedFetch`;
  - an `account` create hook that drops the IdP's tokens;
  - a rotation hook on the OAuth callback.
- **Kept's `session_mfa` gate (S2) already covers OIDC.** It is fail-closed, so an OIDC session
  of a user with TOTP is pending until TOTP is proven in it.
- **No new tables or columns.** `genericOAuth` uses the existing `auth.account` and
  `auth.verification`.

Code: `docs/spikes/code/step6/oidc/`:
- `auth.ts`: a copy of `apps/server/src/auth/auth.ts`, with imports re-pointed and the OIDC wiring
  added. It is marked `S6.7`; everything else is unchanged.
- `oidc.ts`: the shape of T16's `src/auth/oidc.ts`: env parsing, guarded discovery, the provider
  config, the provisioning policy, the hooks.
- `run.ts`: the runner (its header says how to run it):
  1. creates the scratch database `kept_spike6_oidc` on 5452 as `kept_owner`;
  2. applies the migrations **as of HEAD** (`git archive`), so another agent's uncommitted
     `0048` was never applied;
  3. drives the flows against the mock;
  4. drops the database. The runner printed `scratch database dropped: true`.
- `results-2026-09-30.jsonl`: every case, one line each, with its evidence. It holds no cookies,
  tokens or secrets.

The client secret and the auth secret were generated in-process and never written anywhere.

## The checks

The Kept configuration under test is the one in `oidc.ts` and the `S6.7` block of `auth.ts`. In
the cases below, "refused" means:
- the callback redirected to `errorCallbackURL?error=<code>`;
- no session was created;
- no `auth.user` or `auth.account` row was created (both checked with SQL).

### 1. Sign-in reaches only an existing, linked account; no auto-link on email (D176, D127): PASS with fixes

| Case | Result |
|---|---|
| The IdP asserts Bruce's existing, verified email under a new `sub` | `error=account_not_linked`; 0 OIDC accounts |
| Bruce links explicitly: `/link-social` from his fresh session | linked (`account_id = idp-bruce`) |
| That `sub` then signs in | a session for Bruce |
| A different `sub` with Bruce's email, after the link | `account_not_linked` |
| `/link-social` from a session older than 600 s | 403 `SESSION_NOT_FRESH` |
| A link where the IdP email differs from the account's | `error=email_does_not_match` (Better Auth: `allowDifferentEmails` false) |
| An id_token posted straight to `/sign-in/social` (no redirect) | 404 `ID_TOKEN_NOT_SUPPORTED`: without Better Auth's own `idToken` config the provider has no direct id_token sign-in |

**Kept-side fixes:**
- **`account.accountLinking: { enabled: true, disableImplicitLinking: true, allowDifferentEmails:
  false, trustedProviders: [] }`.** Kept's `auth.ts` sets none of this today. Better Auth's
  default links a verified IdP email to an existing verified user, as the stock run below shows.
  This is needed for Google and Apple as well.
- **A fresh session for `/link-social`.** Better Auth's `/link-social` uses `sessionMiddleware`
  only, not a freshness check (`api/routes/account.mjs`). `kept-oidc` adds a before-hook: a
  session created less than `session.freshAge` ago (600 s, `FRESH_SESSION_SECONDS`), else 403
  `SESSION_NOT_FRESH`. The existing `session_mfa` gate already refuses `/link-social` to a
  pending session, because it isn't on the allow-list.
- **Trap: don't use `freshSessionMiddleware` as the hook handler.** The first run did, and
  `/link-social` answered 200 with `{ session: { … token … } }`. A before-hook that returns a value
  short-circuits the endpoint, and that middleware returns the session. The hook now checks the
  age itself, using `getSessionFromCtx`.
- The account key is `sub` (`accountSubject`), never the email.

### 2. `email_verified` false is refused: PASS with a fix

| Case | Result |
|---|---|
| `email_verified: false` | `error=email_unverified`, no user |
| `email_verified` missing | `email_unverified` |
| `email_verified: "true"` (a string) | `email_unverified` |
| `email_verified: false` plus a claim literally named `emailVerified: true` | `email_unverified` |
| An already-linked account whose IdP now says unverified | the sign-in is refused, `email_unverified` |

**Kept-side fix: `user.validateUserInfo`** (`externalIdentityPolicy` in `oidc.ts`). It is Better
Auth's provisioning gate. It runs before `create-user`, `link-account` and OAuth `sign-in`, and it
fails closed (`utils/validate-user-info.mjs`). For `source.method === 'oauth'`, it refuses unless
`user.emailVerified === true`.

The provider's `getUserInfo` sets `emailVerified: claims.email_verified === true` **after**
spreading the claims. Stock `genericOAuth` spreads the decoded id_token **after** setting
`emailVerified` (`fetchUserInfo` in `plugins/generic-oauth/index.mjs`), so an IdP claim named
`emailVerified` overrides it. The stock run shows it: that account was linked.

Better Auth's own `requireEmailVerification` provider option is **not** the fix. Its type
documentation says the user and account "are still created or linked" and only the session is
withheld.

### 3. A `.invalid` email is refused: PASS with a fix

`someone@managed.invalid` and `SOMEONE@Example.INVALID` were both tried, verified and carrying an
allowed group. Both gave `error=email_undeliverable`, with no user. This is the same
`validateUserInfo`, through `isUndeliverableEmail`.

The policy returns early for anything that isn't OAuth, so managed accounts are unaffected: the
admin plugin's `createUser` still created `<uuid>@managed.invalid` with the policy on.
Email-and-password sign-up also still works; the cast here was created through it.

### 4. The session gets Kept's `session_mfa` gate (V32): PASS, no fix needed

| Case | Result |
|---|---|
| Ibrahim (TOTP on) links OIDC from his satisfied session | linked |
| Ibrahim signs in with OIDC | `resolveSession` gives `{ twoFactorEnabled: true, mfa: false, mfaPending: true }`; `gateSession` gives 403 `mfa_required`; Better Auth's `/list-accounts` gives 403 `MFA_REQUIRED` |
| `/two-factor/verify-totp` in that session | 200; `{ mfa: true, mfaPending: false }` |
| Bruce (no 2FA) signs in with OIDC | allowed, `mfa: false` (so `require_2fa` locations stay hidden, §7.14) |

This is what S2 predicted: the gate is fail-closed, so the new sign-in path is pending by
default.

**Related gap, fixed here: rotating the previous session at sign-in.**
- `security.ts`'s rotation hook (`SIGN_IN_SESSION_PATHS`) doesn't cover the OAuth callback. The
  stock instance, which has `keptSecurity` exactly as today, left the browser's previous session
  alive after an OIDC sign-in.
- Hooks see the callback as **`/callback/:id`**.
- **A successful callback reaches after-hooks as an `APIError` with `statusCode` 302**, because the
  endpoint throws its redirect. So `security.ts`'s `if (isAPIError(ctx.context.returned)) return`
  would skip it.
- The spike's copy of the hook treats 302 as success on that path. With it, the previous session
  was deleted.
- T16 adds `/callback/:id` to `SIGN_IN_SESSION_PATHS` and makes that guard accept a 302 there.
- A link callback creates no `newSession`, so the hook leaves the linking session alone.

### 5. Autoprovision only for an allowed domain or group (D127, D176): PASS with a fix

Configuration: `KEPT_OIDC_AUTOPROVISION_DOMAINS=example.org` and
`KEPT_OIDC_AUTOPROVISION_GROUPS=kept-family`.

| Case | Result |
|---|---|
| `talia@example.org` | created, `email_verified` true, `onUserCreated` ran once (the `ensureAccount` hook) |
| `Peter@EXAMPLE.ORG` | created (the domain is compared lower-cased) |
| `someone@example.com`, no group | `error=signup_closed`, no user, no hook |
| `x@evil-example.org`, `x@example.org.evil.net`, `x@sub.example.org` | refused: exact match on the part after the last `@`; no wildcard |
| `groups: ["staff", "kept-family"]`, or `groups: "kept-family"` | created |
| `groups: ["staff"]` | refused |
| `roles: ["kept-family"]` (another claim name) | refused: the claim name is configuration (`KEPT_OIDC_GROUPS_CLAIM`, below) |
| An invite (see below), different domain | created |
| An email-bound invite, but a different verified email | `invite_email_mismatch` |
| An unknown invite token | `signup_closed` |
| An invite forged in the client's `additionalData` (both `keptInvite` and `serverContext` keys) | `signup_closed` |

**Kept-side fix: the same `validateUserInfo`.** On `create-user` it allows:
- an invite, or
- for the OIDC provider only, an allowed domain or group. Google and Apple never autoprovision.

Anything else is `signup_closed`. `createUser` throws before its insert, so a refusal leaves no
row.

**How the invite travels ("existing or invited accounts", D127):**
1. `kept-oidc`'s before-hook on `/sign-in/social` looks the invite up from
   `additionalData.inviteToken`.
2. It stores the invite with `addOAuthServerContext`.
3. `validateUserInfo` reads it back with `getOAuthState().serverContext`.

Better Auth documents `serverContext` as server-trusted and the top-level `additionalData` keys as
client-supplied (`api/state/oauth.d.mts`). The forged case confirms the distinction.

### 6. Discovery goes through the SSRF guard (D128): PASS with a fix; loopback routed with `allowPrivate: true`

**Stock `genericOAuth` can't be guarded:**
- `discoveryUrl` is fetched with `betterFetch`, which resolves `globalThis.fetch` at call time
  (`@better-fetch/fetch` 1.3.2).
- The JWKS is fetched with jose's default fetch (`createRemoteJWKSet(jwksUrl)` with no options).
- Token exchange and userinfo also use `betterFetch`.
- None of these takes a custom fetch.
- The run replaced `globalThis.fetch` with a tripwire. The stock instance's discovery hit the
  tripwire (`http://127.0.0.1:18790/kept/.well-known/openid-configuration`), and the provider was
  skipped (`providerRegistered: false`).

**Kept-side fix** (`oidc.ts`):
- `discoverOidc(issuer, guardedFetch(...))` fetches `<issuer>/.well-known/openid-configuration`.
  It requires `issuer` to equal the configured string exactly; a trailing `/` was refused as
  `issuer_mismatch`. It requires `authorization_endpoint`, `token_endpoint` and `jwks_uri`, all
  https when the issuer is https.
- `genericOAuth` then gets **explicit** endpoints: `authorizationUrl` only, with no `discoveryUrl`,
  `tokenUrl` or `userInfoUrl`.
- `getToken` builds the request with Better Auth's `authorizationCodeRequest` and POSTs it through
  the same fetch; `getOAuth2Tokens` parses the answer.
- `getUserInfo` verifies the id_token with jose's `jwtVerify`: signature, `iss`, `aud` and `exp`,
  against `createRemoteJWKSet(jwks_uri, { [customFetch]: guardedFetch })`. It falls back to
  userinfo through the same fetch only if the id_token has no email, and then requires the same
  `sub`.
- Without `tokenUrl`, Better Auth can't refresh the IdP's access token. Kept never needs to: it
  calls nothing at the IdP after sign-in.

**Proof (tripwire on for every Kept flow):**
- one full sign-in made exactly `POST /kept/token` and `GET /kept/jwks` through the guard;
- boot discovery made `GET /kept/.well-known/openid-configuration`;
- all flows made 31 guarded calls and **0 unguarded**.

**How the loopback provider was routed (honestly):**
- With `allowPrivate: false`, the issuer `http://127.0.0.1:18790/kept` was refused before connect
  (`PrivateAddressError`, code `private_address`).
- A hostname whose (stubbed, via the guard's `resolve` option) DNS answer is 127.0.0.1 was refused
  at connect time.
- The successful flows ran with **`allowPrivate: true`**, the self-host switch
  (`instance_settings.ssrf_allow_private`). In `guardedFetch` that is a plain undici `Agent` with
  no address check. Only `redirect: 'error'` still applies.
- So the private-address refusal was proven on refusal cases only. The spike could not also
  connect to a loopback IdP with the check on; the guard's own tests (`net/ssrf.test.ts`) cover
  public addresses.
- **Consequence for self-hosters:** an IdP on the LAN (Authentik, Keycloak and so on) needs
  `ssrf_allow_private` on. T16 reads it at boot with `allowPrivateAddresses(pools)`
  (`ai/runtime.ts`).

**Not tested:**
- **Nonce.** The authorize request carried PKCE `S256` and `state` but no `nonce`. Better Auth
  sends a nonce only when the provider has its own `idToken` config, which exists only on its
  discovery path. The id_token comes from the token endpoint over the back channel, bound to the
  code by PKCE. My understanding of OIDC Core is that `nonce` is optional in the code flow; that
  is from memory, not re-read here.
- **RFC 9207 `iss`.** For the same reason, Better Auth has no `provider.issuer` to compare a
  callback `iss` with. With one configured IdP a mix-up has nowhere to come from (inferred). If
  wanted, T16 can add a before-hook on `/callback/:id` that compares a present `iss` with the
  configured issuer.

## Also found

- **IdP tokens are kept by default.** Stock stores the access, refresh and id tokens in
  `auth.account` (`tokensStored: true`).
  - Kept's fix: a `databaseHooks.account.create.before` that nulls them for `providerId: 'oidc'`,
    plus `account.updateAccountOnSignIn: false`.
  - The linked account's three token columns were `null`.
- **`validateUserInfo` applies to every `createUser`.** It needs an endpoint context and a
  `source` (`db/internal-adapter.mjs`). Kept's current `auth.api.*` callers pass both (managed
  accounts and sign-up were checked here). A future direct `internalAdapter.createUser` with no
  `source` would throw `validation_source_missing`.
- **OAuth state is stored in `auth.verification`.** Better Auth's default for a stateful setup is
  `storeStateStrategy: 'database'` (`context/create-context.mjs`). It worked with Kept's hashed
  verification identifiers.
- **Error codes the web sign-in must render** (T22, five languages), from `?error=`:
  - `account_not_linked`, `email_unverified`, `email_undeliverable`, `signup_closed`,
    `invite_email_mismatch`, `email_does_not_match`;
  - 403 `SESSION_NOT_FRESH` from `/link-social`;
  - Better Auth's own codes (`oauth2/errors.mjs`), e.g. `invalid_code`, `unable_to_get_user_info`.
- **Boot-time discovery is a single point.** `genericOAuth`'s config is fixed when the auth
  instance is built (Q16's premise), so the endpoints must be known at boot. If the IdP is down
  then, OIDC stays off until a restart.
  - Proposal for T16: try discovery at boot with a short retry, e.g. for 60 s. On failure, start
    without OIDC and show an admin status row naming the reason (`private_address`,
    `issuer_mismatch`, `insecure_endpoint`, `http_status`), with "fix and restart". Not built
    here.

## Stock, for comparison (Better Auth defaults + `genericOAuth` with `discoveryUrl`)

Run with the global `fetch` allowed and none of Kept's OIDC rules:
- an IdP asserting Louis's verified email under an attacker's `sub` was **auto-linked and signed
  in as Louis**;
- `email_verified: false` plus a claim `emailVerified: true` was treated as verified and linked;
- a stranger's verified email was **signed up**;
- `x@managed.invalid` was **accepted**;
- the tokens were stored;
- the previous session survived the sign-in.

This is the evidence that none of the fixes above is optional.

## Environment variables (Q16): settled

| Variable | Required | Meaning |
|---|---|---|
| `KEPT_OIDC_ISSUER` | turns OIDC on | The issuer URL exactly as the IdP's discovery document states it. Kept fetches `<issuer>/.well-known/openid-configuration` through the SSRF guard. |
| `KEPT_OIDC_CLIENT_ID` | with the issuer | Kept refuses to boot with an issuer and no client id. |
| `KEPT_OIDC_CLIENT_SECRET` | usually | Sent `client_secret_post`, Better Auth's default. `genericOAuth` types it optional (a public client with PKCE); only the confidential case ran here. Never logged; never in D180's hash. |
| `KEPT_OIDC_NAME` | no (default `OIDC`) | "Sign in with <name>". |
| `KEPT_OIDC_AUTOPROVISION_DOMAINS` | no (empty = off) | Comma-separated. Exact, case-insensitive domains; no wildcard, no subdomains. |
| `KEPT_OIDC_AUTOPROVISION_GROUPS` | no (empty = off) | Comma-separated, exact. Matched against the groups claim, which may be an array or a single string. |
| **`KEPT_OIDC_GROUPS_CLAIM`** (new) | no (default `groups`) | The spike showed a group under another claim name is not seen. Which claim a given IdP uses is IdP-specific and was not verified for any real IdP. |
| **`KEPT_OIDC_SCOPES`** (new) | no (default `openid email profile`) | For an IdP that emits groups only for an extra scope. Inferred need; not verified for any real IdP. |

Recommendations:
- **D180's configuration hash** covers the issuer and client id (the plan's rule). I recommend
  also hashing the name, both autoprovision lists and the groups claim: they change who can get
  in.
- **Autoprovision is off unless a list is set.** The provider id is fixed as `oidc`, so the
  callback is `<public URL>/api/v1/auth/callback/oidc`, the redirect URI an admin registers at the
  IdP. The admin status row should show it.

## Tables

**None.**
- The plugin object has no `schema` (`plugins/generic-oauth/index.mjs`).

## What changes in the plan

**T7 (tables and instance settings):**
- Drop "generic-OAuth tables" from its file list and from Step 2. S6.7 found none.
- Step 3: under Q16, OIDC autoprovision lives in `KEPT_OIDC_AUTOPROVISION_*`. That makes the
  `oidc_autoprovision_issuers` instance setting (engineering spec §1.2's list) redundant with one
  env-configured issuer. Recommend removing it there and from §1.2, rather than keeping two
  sources. `oidc_config_hash` stays.

**T16 (generic OIDC):**
- **Dependencies:** add `jose` 6.2.12 (MIT) as a direct dependency of apps/server. It is already in
  the tree through better-auth, so the image gains nothing. The plan's dependency table gains the
  row.
- **`src/auth/oidc.ts`** as in the spike:
  - `readOidcEnv`, and `discoverOidc` through `guardedFetch({ allowPrivate: await
    allowPrivateAddresses(pools) })`;
  - `oidcProvider` with explicit endpoints, `getToken`/`getUserInfo` through that fetch, and
    `accountSubject` = `sub`;
  - **never `discoveryUrl`, `tokenUrl` or `userInfoUrl`.**
- **`auth/auth.ts`:**
  - `account: { updateAccountOnSignIn: false, accountLinking: { enabled: true,
    disableImplicitLinking: true, allowDifferentEmails: false, trustedProviders: [] } }`;
  - `user.validateUserInfo` = the external-identity policy (verified, not `.invalid`, and on
    create only by invite or OIDC autoprovision);
  - `databaseHooks.account.create.before` dropping the IdP's tokens;
  - the `kept-oidc` plugin: a fresh session on `/link-social` (not `freshSessionMiddleware` as the
    handler), and the invite into `addOAuthServerContext`.
- **`auth/security.ts`:** add `/callback/:id` to `SIGN_IN_SESSION_PATHS`, and let that path's
  rotation hook treat a 302 `APIError` as success. Also check any other after-hook that should
  see an OAuth sign-in.
- **The invite path:**
  - `findInvite` needs a way for the auth side to read an invite by token: a `kept_app` definer
    function, or the invite code's own lookup (T16 decides).
  - `ensureAccount` must consume the invite. The serverContext invite id should be readable in
    `databaseHooks.user.create.after` through `getOAuthState()`. That is inferred and **not
    tested here**.
- **Boot:** discovery with a short retry. On failure, OIDC is off, with an admin status row (the
  reason codes above).
- **`config/env.ts`:** the eight variables above. Add them to §7.11, `.env.example` and
  `compose.env.example`.
- **Tests** (one each, from this spike's cases):
  - no auto-link on email;
  - a different `sub` with the same email;
  - an explicit link from a fresh session, and refusal from a stale one;
  - a link with a different email;
  - no id_token sign-in;
  - `email_verified` false, missing, a string, and overridden by an `emailVerified` claim;
  - a linked account turned unverified;
  - `.invalid`;
  - the pending `session_mfa` then TOTP; no 2FA gives `mfa` false;
  - rotation on the callback;
  - allowed and lookalike domains, groups, the claim name, the invite, a forged invite;
  - loopback refused with `allowPrivate` false;
  - issuer mismatch;
  - IdP tokens not stored;
  - managed accounts unaffected.

  I recommend an **in-process** OIDC stub for vitest over this 416 MB container: a small HTTP
  server signing with jose, with the same login-with-claims shape. The container stays a manual
  check.
- **Open for the maintainer:** a user with TOTP who signs in with an IdP that already did MFA is
  still asked for Kept's TOTP. That is D176 as written ("two-factor at the session layer for
  every sign-in method"). Trusting the IdP's `amr`/`acr` would be a new decision; the spike does
  not propose it.

**T22 (web):**
- "Sign in with <name>";
- the error codes above, in five languages;
- the admin row shows the callback URL to register at the IdP, and the discovery failure reason.
