# Spike S1 (V33): Better Auth and pg-boss under non-owner roles

Date: 2026-09-26. Result: **proven, no fallback taken.**

## What was proven

- **Better Auth 1.7.6 runs on the Drizzle adapter with its tables in schema `auth`, logged in
  as `kept_auth`.** `auth.api.signUpEmail` writes `auth."user"`, `auth.account` and
  `auth.session` through a `kept_auth` pool; nothing in Better Auth needs the owner role at
  runtime. Test: `apps/server/src/auth/auth.test.ts`.
- **UUIDv7 ids.** Users and sessions get version-7 ids whose embedded time is within 1 s of the
  insert.
- **Role isolation holds.** `kept_auth` gets `permission denied` on `public.*`, `pgboss.*` and
  `kept_meta.*`; `kept_app` gets `permission denied` on `auth.*`.
- **pg-boss 12.34.0 runs with its migrations off under non-owner roles.** `kept migrate` (as
  `kept_owner`) installs the schema; a `kept_system` instance starts with `migrate: false`, runs
  workers, cron and maintenance (`supervise()`), and refuses to start (`pg-boss is not installed`)
  against a schema it would have had to create. Test: `apps/server/src/jobs/boss.test.ts`.
- **Enqueue inside the request transaction (D94).** `boss.send(name, data, { db })`, with `db`
  wrapping the `kept_app` transaction's client, creates the job only if that transaction commits:
  a committed send reaches the `kept_system` worker, a rolled-back one leaves nothing to fetch.

## Exact config

### Better Auth (`apps/server/src/auth/auth.ts`)

- CLI: `@better-auth/cli` stops at 1.4.x; from 1.5 the CLI is the npm package **`auth`**
  (version-locked to better-auth). `pnpm dlx auth@1.7.6 generate --config <file> --output <file>`
  with `drizzleAdapter({}, { provider: 'pg', schemaName: 'auth' })` and
  `advanced.database.generateId: 'uuid'` generates `pgSchema('auth')` tables with `uuid` ids.
- Kept's adjustments to the generated schema (`apps/server/src/db/schema/auth.ts`): every
  timestamp is `timestamptz`; ids default to Postgres 18's `uuidv7()`. **Correction from S2:**
  `auth.verification.id` must be `text`, because `reserveVerificationValue()` writes a
  deterministic non-UUID id (migration `0002`; see `2026-09-26-s2.md`). `drizzle.config.ts`
  `schemaFilter` gains `'auth'`. drizzle-kit emits a bare `CREATE SCHEMA "auth"`; migration
  `0001_auth_tables.sql` changes it to `IF NOT EXISTS`, because `0000` creates the schema.
- Options, names read from `@better-auth/core/dist/types/init-options.d.mts`:
  - `database: drizzleAdapter(drizzle(authPool, { schema }), { provider: 'pg', schema, transaction: true })`
    where `schema` is `betterAuthTables` keyed by model name (`user`, `session`, `account`,
    `verification`, `twoFactor`, `passkey`, `rateLimit`). The adapter's `schemaName` option only
    affects CLI generation; queries are schema-qualified by `pgSchema('auth')`.
  - `advanced.database.generateId: () => uuidv7()` (uuid@14). The option takes a function, `false`,
    `'serial'` or `'uuid'`; `'uuid'` would give v4.
  - `secret: env.KEPT_AUTH_SECRET`, `baseURL: env.KEPT_PUBLIC_URL`, `basePath: '/api/v1/auth'`.
  - `telemetry: { enabled: false }`.
  - `disabledPaths: ['/admin/impersonate-user', '/admin/stop-impersonating']`: the admin plugin
    is there for ban and session revocation only, and impersonation contradicts D164.
- Plugins: `twoFactor` (`better-auth/plugins`), `passkey` (**separate package
  `@better-auth/passkey@1.7.6`**; not in `better-auth/plugins` in 1.7), `magicLink`, `username`,
  `admin`. `@simplewebauthn/server@13.3.3` is a direct dependency only so `tsc` with
  `declaration: true` can name the passkey plugin's types.
- Better Auth's runtime schema check (`advanced.database.validateSchema`, default on) accepts the
  adjusted schema (no mismatch logged).

### pg-boss (`apps/server/src/jobs/install.ts`, `apps/server/src/jobs/boss.ts`)

- Install: `runMigrations` runs drizzle's migrations, then `installPgBoss(client)` on the same
  `kept_owner` connection, inside Kept's advisory lock:
  - not installed (`to_regclass('pgboss.version')` is null): run `getConstructionPlans('pgboss')`
    (it wraps itself in `BEGIN … COMMIT` and takes pg-boss's own advisory lock);
  - installed at an older version: run `getMigrationPlans('pgboss', version)`;
  - the target version is `pgboss.schema` in pg-boss's `package.json` (42 for 12.34.0).
- Runtime (`createBoss`): `new PgBoss({ connectionString: <kept_system>, schema: 'pgboss',
  migrate: false, createSchema: false, reindex: false, supervise, schedule })`.
  `reindex: false` because `kept_system` doesn't own the job indexes. A process that only sends
  must still `start()`: `send()` reads the queue cache that `start()` initialises.
- Send in a transaction: `sendInTx(boss, client, name, data, options)` passes
  `{ db: { executeSql: (text, values) => client.query(text, values) } }`.
- Grants, found by running `send()` as `kept_app` until it stopped failing:
  - `kept_app`: `USAGE` on schema `pgboss`; `INSERT, SELECT (id, start_after)` on
    `pgboss.job_common` (send inserts straight into the queue's table, not the partitioned
    parent, and `RETURNING id` needs column SELECT; `start_after` is returned for notify
    queues); `SELECT` on `pgboss.queue` (joined for queue defaults). `job_now()` is executable by
    PUBLIC. It can't read job data, update or delete jobs.
  - `kept_system`: `USAGE` on the schema; `SELECT, INSERT, UPDATE, DELETE` on all tables and
    `USAGE, SELECT` on sequences, plus default privileges for tables `kept_owner` creates there
    later.

## Constraints this leaves

- **Queues must be unpartitioned** (the default). `createQueue(name, { partition: true })` runs
  DDL (`CREATE TABLE`), which `kept_system` can't do. Unpartitioned queues all live in
  `pgboss.job_common`, which is what the grants name.
- **pg-boss upgrades are untested.** The upgrade branch runs `getMigrationPlans()`, which inlines
  pg-boss's async index builds after its `COMMIT`. If a future migration builds an index
  `CONCURRENTLY`, it can't run in one simple-query batch and the branch will need to split the
  statements. Verify on the first pg-boss release that bumps `pgboss.schema`.
- Index rebuilds (`getReindexCommands()`) are an operator task, since the serving role doesn't
  own the indexes.

## Fallbacks

None taken. Better Auth accepted the separate schema, and pg-boss enqueues on our transaction's
client, so neither the `auth_`-prefixed tables in `public` nor the outbox relay was needed.
