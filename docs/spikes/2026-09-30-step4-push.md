subscribe, and the Chrome DevTools Protocol path works in full Chromium's new headless mode.**
T15 sends with `web-push` 3.6.7 as planned. T24 and T30 test the worker's `push` and
`notificationclick` handlers through `ServiceWorker.deliverPushMessage`, and stub `subscribe()` in

Code: `docs/spikes/code/step4/push/`:

- `recorder.mjs`: what `web-push` sends, and how its errors read, against a local HTTPS recorder;

## The server side (`recorder.mjs`)

**Keys.** `generateVAPIDKeys()` returns unpadded base64url:

- a 65-byte public key (87 characters);
- a 32-byte private key (43 characters).

`src/vapid-helper.js` validates exactly these lengths and the alphabet. T2's `KEPT_VAPID_*`
validation copies it.

**The subject** must be an `https:` URL or a `mailto:` address. For a `localhost` subject the
library only warns ("unsupported by Apple's push notification server"). T2's `vapidSubject()`
therefore skips an `https://localhost` public URL.

**The request** (default `aes128gcm`, RFC 8291):

```
POST <endpoint>
TTL: 3600
Content-Type: application/octet-stream
Content-Encoding: aes128gcm
Authorization: vapid t=<JWT>, k=<public key>
Urgency: normal | high …     (only when set; the recorder saw "normal" by default)
Topic: <≤ 32 URL-safe base64 characters>   (only when set)
```

- **Body size.** An 80-byte payload became 183 bytes. The body opens with a 16-byte salt, then
  record size 4096, then a 65-byte key id.
- **The legacy `aesgcm` encoding** is opt-in (`contentEncoding: 'aesgcm'`). It sends
  `Encryption: salt=…`, a `Crypto-Key: dh=…;p256ecdsa=…` header and `Authorization: WebPush <JWT>`,
  and its body is 98 bytes. Kept keeps the default.
- **Topic.** A topic over 32 characters, or with any character outside base64url (a `.`), throws
  before sending. A topic like `r<uuid without dashes>` fits exactly: 32 characters.
- **TTL.** The default is four weeks (2,419,200 s). T15 must set its own.

**Responses.** Any status outside 2xx rejects with a `WebPushError`:

| Status | Result |
|---|---|
| 201 | resolves `{statusCode: 201, body: ''}` |
| 404, 410, 413, 429, 500 | rejects `WebPushError`, `statusCode` = the status, `body` = the response text, `endpoint` = the subscription's, message "Received unexpected response code" |

So T15 prunes the subscription on `err.statusCode === 404 || err.statusCode === 410` (L112), backs
off on 429 and 5xx, and treats 413 as a payload bug. `err instanceof webpush.WebPushError` holds.

**Transport, which matters for the SSRF rule (Q12):**

- **`web-push` always speaks TLS.** It uses `https.request` whatever the endpoint's scheme: an
  `http://` endpoint was sent over TLS to the same host and port, and succeeded against the
  recorder. The `https://` check must therefore be Kept's own: T7's CHECK
  `endpoint ~ '^https://'`, and the route.
- **A self-signed certificate is refused** (`DEPTH_ZERO_SELF_SIGNED_CERT`) unless the caller passes
  an agent that trusts it.
- **The `agent` option is honoured only when it is an `https.Agent`.** Anything else is ignored,
  with a `console.warn`.
- **So the private-address refusal (Q12) goes in an `https.Agent`.** T15 builds
  `new https.Agent({ lookup })` from `src/net/ssrf.ts`'s connect-time lookup, which is currently
  internal as `guardedLookup` and will need exporting. As with the undici agent, an IP-literal
  host is checked first, because Node skips `lookup` for a literal. `allowPrivate` is ignored
  for push endpoints.

## The browser side (`run.mjs`)

A page on `http://localhost:<port>` (a secure context) registers `sw.js`, which:

- on `push`: calls `showNotification`, and posts the data to the page;
- on `notificationclick`: calls `openWindow(data.url)`.

The spike used headless runs only; it opened no window on the Mac.

| | Headless shell (Playwright's default) | Full Chromium, new headless (`channel: 'chromium'`) |
|---|---|---|
| `Notification.permission` after `grantPermissions(['notifications'])` | **denied** | granted |
| `pushManager.permissionState({userVisibleOnly: true})` after CDP `Browser.setPermission({name: 'push', userVisibleOnly: true}, 'granted')` | granted | granted |
| `pushManager.subscribe({applicationServerKey})` | `AbortError: Registration failed - permission denied` | the same |
| CDP `ServiceWorker.deliverPushMessage` | delivered, but no notification (permission denied) | **the `push` handler ran**: the page received the data, and `getNotifications()` listed "Kept spike" with the payload as its body |

**Chromium in Playwright has no push service.** Subscribing fails with "permission denied" even
when the push permission reads granted. This matches the plan's warning: headless Chromium's push
service may be unavailable.

**The CDP command** is in playwright-core 1.63.0's `types/protocol.d.ts`:

```
ServiceWorker.deliverPushMessage { origin: string; registrationId: RegistrationID; data: string }
```

Its `registrationId` comes from the `ServiceWorker.workerRegistrationUpdated` event after
`ServiceWorker.enable`. Playwright's `grantPermissions()` has no `push`; CDP
`Browser.setPermission` takes the descriptor `{name: 'push', userVisibleOnly: true}`.

**What T24 and T30 do with this:**

- **Browser.** Launch Chromium with `channel: 'chromium'`, which is still headless. The headless
  shell can't show notifications.
- **Subscribe.** Stub `PushManager.prototype.subscribe` in the page with `addInitScript`: return
  a fixed subscription whose endpoint is the e2e server's local recorder, so the "Enable" flow,
  `POST` of the subscription and Settings' state are real.
- **Receive.** Drive `push` with `deliverPushMessage`, carrying the payload T15 would encrypt, and
  assert the notification (`registration.getNotifications()`).
- **Tap.** Nothing in this CDP version clicks a notification: its `ServiceWorker` domain has
  `deliverPushMessage` and the sync events, and there is no notification-click command. So the
  `notificationclick` handler keeps its URL logic in a small pure function, which a unit test
  covers: same-origin only, and the fallback to Home. The real tap goes on the device checklist.
- **Server.** Tested against the local HTTPS recorder, as here.

A real push service (FCM, Mozilla's, Apple's) is reached only from a real browser. That is on the
device checklist (`2026-09-30-step4-devices.md`).
