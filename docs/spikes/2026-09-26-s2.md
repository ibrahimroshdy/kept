# Spike S2 (V32): two-factor on every sign-in method, and a shared rate limiter

Date: 2026-09-26. Result: **half true.** Better Auth's database rate limiter is shared across
processes. Its two-factor enforcement covers password sign-in only. As the plan says for that
case, Kept builds its own gate. It also builds its own account + IP limiter, because Better Auth
keys on IP + path only.

## What was found

### Two-factor, per method (Better Auth 1.7.6)

The `twoFactor` plugin's only enforcement is an after-hook whose matcher is
`/sign-in/email`, `/sign-in/username` and `/sign-in/phone-number`
(`better-auth/dist/plugins/two-factor/index.mjs`). For those paths it deletes the new session and
answers `{ twoFactorRedirect: true }`.

| Method | Better Auth alone | With Kept's gate | Test |
|---|---|---|---|
| Password (email or username) | challenged; no session until TOTP | same; the session made by the challenge is marked satisfied | `two-factor.test.ts` "password" |
| Magic link (`/magic-link/verify`) | **full session, no second factor** | session is *pending*: 403 until TOTP or a backup code is proven in it | "magic link …" |
| Passkey (`/passkey/verify-authentication`) | **full session**; verifies with `requireUserVerification: false` | with UV: satisfied (counts as two factors, §7.14); without UV: pending | "passkey …" (a software ES256 authenticator in `test/webauthn.ts`) |
| Social / OIDC callbacks | full session (no two-factor hook) | pending by default, because the gate is fail-closed | not testable until step 6 (no provider configured) |

Trust-device cookies (`trustDevice` on verify) would let a password sign-in skip the challenge;
Better Auth then keeps the session without passing through our satisfied marker, so Kept's gate
treats it as pending. The client should not offer "trust this device".

### Rate limiting

- `rateLimit.storage: 'database'` exists and stores counters in the `rateLimit` model
  (`auth.rate_limit`) with atomic conditional increments, so replicas share it. Proven with two
  instances on one database: six sign-ins from one IP, alternating instances, give
  `401 ×5, 429` (`rate-limit.test.ts`).
- The key is **IP + path** (`createRateLimitKey(ip, path)`); there is no account key. It counts
  every request to the path, not only failures.
- It runs in Better Auth's HTTP router (`onRequestRateLimit`), so **`auth.api.*` server calls
  are not rate-limited**. Only requests through `auth.handler` are.
- The client IP comes from `advanced.ipAddress.ipAddressHeaders` (default `x-forwarded-for`),
  single-value only unless `advanced.ipAddress.trustedProxies` is set. In development and test
  it falls back to `127.0.0.1`. Task 17/29 must set `trustedProxies` for the reverse proxy.

## Exact config (kept)

### Better Auth options (`apps/server/src/auth/auth.ts`)

```ts
rateLimit: {
  enabled: true,              // Better Auth defaults this to production only
  storage: 'database',
  window: 60, max: 100,
  customRules: { '/sign-in/*': { window: 60, max: 5 } },   // §3.2: 5/min per IP
},
plugins: [
  twoFactor({ issuer: 'Kept' }),
  passkey({ rpName: 'Kept', rpID: <public host>, origin: <public origin>,
            authentication: { afterVerification: ({ ctx, verification }) =>
              rememberPasskeyVerification(ctx.context, verification.authenticationInfo.userVerified) } }),
  magicLink({ disableSignUp: true, sendMagicLink }),
  username(), admin(),
  keptSecurity({ pool, getSession }),   // Kept's plugin, below
]
```

`customRules` keys are matched against the path relative to `basePath`, with `*` wildcards; a
rule replaces Better Auth's built-in special rule for sign-in (3 per 10 s).

### The gate (`apps/server/src/auth/security.ts`, `apps/server/src/auth/session.ts`)

- **Table `auth.session_mfa`** (`session_id` PK → `auth.session` on delete cascade, `method`,
  `satisfied_at`), written by `kept_auth`. A row means a second factor was proven in that
  session.
- **Marking satisfied** (Better Auth after-hooks, `ctx.context.returned` not an `APIError`):
  - `/two-factor/verify-totp`, `/two-factor/verify-backup-code`, `/two-factor/verify-otp`: the
    session is `ctx.context.newSession` (sign-in challenge, or enrolment, which swaps the session)
    or else `ctx.context.session` (a pending session verifying in place);
  - `/passkey/verify-authentication`: `ctx.context.newSession`, only when the passkey plugin's
    `afterVerification` reported `authenticationInfo.userVerified`. The callback and the hook
    share the request's `ctx.context` object; the flag travels on a `WeakMap` keyed by it.
- **Refusing pending sessions inside Better Auth** (a before-hook on every path except an
  allowlist): if the caller's session belongs to a user with `twoFactorEnabled` and has no
  `session_mfa` row, throw `APIError('FORBIDDEN', { code: 'MFA_REQUIRED' })`. The allowlist is
  `/get-session`, `/sign-out`, `/sign-in/*`, `/magic-link/verify`, the three second-factor
  verify paths, `/two-factor/send-otp`, `/passkey/generate-authenticate-options`,
  `/passkey/verify-authentication`, `/ok`, `/error`. This matters: without it, a pending session
  could register a new passkey and sign in again with it to skip the second factor. The test
  checks that `generatePasskeyRegistrationOptions` is refused.
- **Kept's own routes:** `resolveSession(auth, authPool, headers)` returns
  `{ userId, sessionId, twoFactorEnabled, mfa, mfaPending }` plus the refresh's response
  headers; `gateSession()` turns it into `401 unauthenticated`, `403 mfa_required`, or a
  `{ userId, mfa }` scope for `withScope()`.
- **Deviation from the plan's formula.** The plan wrote
  `mfa = satisfied || user has no 2FA || passkey with UV`. That would give a user who never
  enrolled `app.mfa = true`, and show them `require_2fa` locations, which §7.14 and D190 forbid
  ("a member who hasn't enrolled can still sign in, but that location is hidden until they
  enrol"). So there are two fields: `mfa` = satisfied in this session (TOTP, backup code, OTP, or
  passkey with UV), and `mfaPending` = enrolled and not satisfied. `mfaPending` is what gets
  blocked. A user who never enrolled gets `mfa = false, mfaPending = false`.
- **Second-factor attempts inside a pending session.** Better Auth's verify-totp has attempt
  limits and a lockout only in the sign-in-challenge branch. When a session already exists it
  has neither, so a pending magic-link session could guess codes at the IP limit. Kept applies
  its account limiter there, keyed on the user alone. Five wrong codes, then delays
  (`SIGN_IN_DELAYED`). Tested.

### Account + IP limiter (`apps/server/src/auth/sign-in-limiter.ts`)

- **Table `auth.sign_in_failures`** (`key` PK, `window_start`, `count`, `last_failure_at`).
  `key` = SHA-256 of kind, the lower-cased account identifier (email or username) and the client
  IP. The raw email and IP are not stored.
- Before-hook on `/sign-in/email` and `/sign-in/username`: refuse with
  `429 { code: 'SIGN_IN_DELAYED', retryAfter }` and `X-Retry-After` when
  - 20 failures in the current 1-hour window: blocked until the window ends; or
  - after 4 free failures, the time since the last failure is less than
    `2^(failures−4)` s (2, 4, 8, … capped at 300 s).
- After-hook: a `401` counts one failure (an atomic upsert that restarts a lapsed window); a
  success deletes the row. Every decision uses the database clock, so replicas agree.
- Proven with two instances: five failures split across both, then the right password is
  delayed on either instance; the same account from another IP is not delayed (so there is no
  lockout of others); after the delay the right password works and clears the row; at 20 the
  wait is the rest of the window.

## Other finding (affects S1's schema)

`auth.verification.id` must be **text**, not uuid. `internalAdapter.reserveVerificationValue()`
writes a deterministic id (the base64url SHA-256 of `reserve:<identifier>`) with `forceAllowId`.
Magic-link verification uses it for users whose email isn't verified yet. Migration `0002`
changes the column to text (default `uuidv7()::text`). The generator's `uuid` type is wrong for
this model.

## Not done here (belongs to task 17's security suite)

- The §3.2 "password reset / magic link 3 per hour per account" limit. Better Auth's magic-link
  plugin only limits per IP (5 per minute per path by default; our `/sign-in/*` rule applies to
  `/sign-in/magic-link` too).
- Pruning `auth.sign_in_failures` rows whose window has lapsed. That needs a system job, with
  `kept_system` granted DELETE on that one table (task 24).
- A before-hook error from the gate is Better Auth's `{ code: 'MFA_REQUIRED' }`. Kept's own
  routes answer `{ code: 'mfa_required' }`. Task 17 should map the Better Auth code when it
  mounts the handler, if one error vocabulary is wanted.

## Fallbacks

Taken, as written in the plan: Kept's own two-factor gate (session flag plus route gate), and
Kept's own account + IP limiter, because Better Auth has neither. Better Auth's database-backed
IP limiter is used as is.
