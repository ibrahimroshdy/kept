## What ran

```sh
helm lint .                              # 1 chart linted, 0 failed ([INFO] icon is recommended)
helm template h1 . | kubeconform -strict -summary -kubernetes-version 1.37.0 -cache <dir> \
  -schema-location 'https://raw.githubusercontent.com/yannh/kubernetes-json-schema/8df8a883b68a24a104b4a9e43c1288090ae60b3b/{{.NormalizedKubernetesVersion}}-standalone{{.StrictSuffix}}/{{.ResourceKind}}{{.KindSuffix}}.json'
# Summary: 2 resources found parsing stdin - Valid: 2, Invalid: 0, Errors: 0, Skipped: 0
helm template h1 . --set resources.requests.cpu=true | kubeconform -strict …
# Deployment h1-kept is invalid: … /resources/requests/cpu: got boolean, want null or string … (exit 1)
helm package . && helm push trivial-0.1.0.tgz oci://localhost:5099/charts --plain-http
```

Timings (M1 Pro): kubeconform's **first run 29 s** (it downloads the schemas; the cache holds
748 KiB for these two kinds), **0.5 s cached**; `helm lint` and `helm template` well under a second.
So ci-local's `helm` step is cheap once the cache is warm.

- **Pin the schemas by commit.** kubeconform's `default` location is the fork's `master` branch
  (its README: an alias for `…/kubernetes-json-schema/master/{{.NormalizedKubernetesVersion}}…`),
  which changes under a pinned tool. The commit-pinned `-schema-location` above worked and is
  what T16 uses, with `-cache` in a git-ignored directory (e.g. `.tmp/kubeconform`). Template
  variable names are from kubeconform v0.8.0's README.
- **Offline CI:** a cold cache needs `raw.githubusercontent.com`. With the cache warm the step runs
  offline (inferred from kubeconform's cache behaviour: the second run made no slower download;
  not run with the network blocked).

## The chart as an OCI artifact, signed

`helm push` to the throwaway registry (`registry:3.1.2`, below) gave
`localhost:5099/charts/trivial:0.1.0`, manifest `sha256:f09c394d…`, config media type
`application/vnd.cncf.helm.config.v1+json`, one layer
`application/vnd.cncf.helm.chart.content.v1.tar+gzip`, and `org.opencontainers.image.*`
annotations from `Chart.yaml`. The manifest carries `org.opencontainers.image.created` (the package
time), so **re-packaging the same chart gives a new digest**: the release signs the digest it pushed,
never a recomputed one.

cosign v3.1.3 signed that digest with a key and verified it (details in the
[release spike](2026-10-06-step8-release.md)): `cosign sign --key cosign.key --signing-config
no-tlog.json --allow-http-registry localhost:5099/charts/trivial@sha256:f09c…` then `cosign verify
--key cosign.pub --insecure-ignore-tlog --allow-http-registry …` → "The signatures were verified
against the specified public key"; the wrong key → "no matching attestations … Found: 0,
Expected 1". The registry has no referrers API (404), so cosign stored the signature under the tag
`sha256-<digest>` beside `0.1.0`.
